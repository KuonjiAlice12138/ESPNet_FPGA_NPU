# Workplan 0817 - 当前 INT8 NPU 精度、性能与硬件架构

本文用于组会汇报，内容以当前 P7 INT8 硬件、PARAM v4 编译格式和已完成的板级测试为准。硬件采用 100 MHz PL 时钟；PS 端 ARM 计时器为 33.333 MHz。

## 2. 当前版本推理性能

### 2.1 计时口径

ARM `CNTPCT_EL0` 频率为 `33,333,000 Hz`，RTL counter 统计 PL 的 100 MHz 周期。二分类首张图的闭环结果为：

| 项目 | 数值 |
|---|---:|
| RTL 总周期 | 51,319,833 cycles |
| PL 等效时间 | 513.198 ms |
| ARM 计时 | 17,106,599 ticks = 513.203 ms |
| ARM/RTL 差值 | 约 5 us |
| 500 张总时间 | 256.602 s |

因此当前二分类单张推理延时约为 `513.2 ms`。最后一次成功的 20 类板级基线为：

| 模型 | RTL 周期 | 100 MHz 等效时间 | 相对二分类 |
|---|---:|---:|---:|
| 二分类 | 51,229,815 cycles | 512.298 ms | - |
| 20 类 | 51,393,493 cycles | 513.935 ms | +0.32% |

20 类没有出现按类别数线性增长，原因是末层仍使用一个 32 通道输出 tile，多类别代价主要集中在最终分类输出，而不是复制整套卷积阵列。

|---|---:|---:|---|

### 2.3 Stage 的解读边界

stage counter 每个周期只记录一个当前阶段，因此它是时间归类，不是多个模块的独立 busy 计数器。

- `CONV_ROW_DATAPATH` 内部包含窗口生成、SA 计算、partial sum 传递和卷积后处理，不能直接等同于纯 MAC 时间。
- `PPU_ROW_CONSUME` 处理普通卷积输出行；`PPU_BLOCK5_FINAL` 处理需要多路 scratch 和残差合并的 Block5 最终行。
- `VEC_FIXED` 是独立向量算子阶段，与卷积行内部的 PPU 不是同一个执行入口。
- 当前上采样输出在卷积行消费者路径中完成，因此独立 `UPSAMPLE_OUT` 桶可能为 0；这不代表没有产生全分辨率 mask。
- 当前卷积行和 PPU 使用共享 row buffer，外层控制仍是顺序的；stage 周期不能被解释为 Conv 与 PPU 已经完全并行。

当前优化重点应放在 `CONV_ROW_DATAPATH`，其次是 Block5 和独立 Vec 阶段，而不是继续优化参数加载或 PS 侧 SD 读写。

## 3. 硬件微架构与卷积数据通路

### 3.1 顶层硬件结构

下面的字符画对应系统级框图。左侧 PS 负责软件控制和外部存储访问，右侧 PL 负责片上数据流和计算；两侧通过 AXI 接口连接。

```text
+----------------------+        +----------------------------------------------------------+
|          PS          |        |                          PL NPU                          |
|                      |        |                                                          |
| +------------------+ |        | +----------------------------------------------------+   |
| | ARM + AXI ctrl   | |        | |       Main Ctrl -> Frame DMA -> On-chip Mem        |   |
| +------------------+ |        | +----------------------------------------------------+   |
| +------------------+ |        | +----------------------------------------------------+   |
| | DDR4 in/param    | |        | |     Conv: Window -> FIFO -> MAC -> Requant/Act     |   |
| +------------------+ |        | +----------------------------------------------------+   |
+----------------------+        | +----------------------------------------------------+   |
                                | |    Row PPU: Add / Affine / Concat / Block5 / WB    |   |
                                | +----------------------------------------------------+   |
                                | |       Vec  ->  AvgPool  ->  Upsample / Mask        |   |
                                | +----------------------------------------------------+   |
                                +----------------------------------------------------------+
```

两条跨芯片连接分别是：`AXI-Lite: ARM -> Main Ctrl`（控制）和 `AXI-MM: DDR4 -> Frame DMA -> On-chip Mem`（数据）。

硬件不保存某一个固定网络的控制状态。编译器将张量位置、卷积参数、量化参数、窗口访问方式和后处理方式写入 PARAM v4；更换支持的模型时，主要替换 PARAM 和权重文件，不改变 MAC 阵列结构。

### 3.2 片上存储与数据复用

输入特征图进入片上缓存后，卷积计算尽量在片上完成。各存储的硬件作用如下：

- **特征图缓存**：保存输入和中间张量，减少反复访问外部存储；
- **共享权重缓存**：一个卷积层装载一次权重，多行复用；
- **窗口行复用**：3x3 卷积相邻输出位置共享输入行和相邻列数据；
- **256-bit 打包访问**：一次搬运多个 INT8 数据，降低存储访问控制开销；
- **Row buffer**：保存一行已经完成卷积量化/激活的结果，交给行级 PPU。

### 3.3 Conv Engine 内部数据通路

以下是以一个输出行和一个 3x3 卷积为例的硬件数据路径。图中“量化/激活”和“行级 PPU”是两个不同的阶段：前者处理卷积 psum，后者处理已经量化后的输出特征。

```text
                           PARAM
                    sched / Ktile / qparam
                              |
                              v
+------------+   +------------+   +------------+   +------------+
| Feature    |-->| Window Gen |-->| Input FIFO |-->| 32x32 MAC  |
| Cache      |   |            |   |            |   | Array      |
+------------+   +------------+   +------------+   +------------+
                                                          |
                                                          v
                                                    +------------+
                                                    | psum FIFO  |
                                                    +------------+
                                                          |
                                                          v
                                                    +------------+
                                                    | Requantize |
                                                    | / Activate |
                                                    +------------+
                                                          |
                                                          v
                                                    +------------+
                                                    | Row buffer |
                                                    +------------+
                                                          |
                                                          v
                                                    +------------+
                                                    | Row PPU    |
                                                    | Add/Affine |
                                                    | Concat/WB  |
                                                    +------------+
```

具体处理顺序：

1. 控制器读取当前卷积的输入、输出、权重、量化和窗口访问描述。
2. 权重装入共享缓存，随后复用于当前卷积的所有输出行。
3. Window Generator 从片上特征图缓存读取窗口，完成边界处理和相邻位置的数据复用；它使用 PARAM 中已经编译好的窗口计划，不在运行时重新理解网络形状。
4. 每个输出位置的窗口数据按 K tile 送入输入 FIFO。一个 K tile 最多包含 32 个输入数据 lane。
5. MAC 阵列同时计算最多 32 个输出通道；每个输出通道的 partial sum 在多个 K tile 之间连续累加。
6. 一个输出位置的所有 K tile 完成后，最终 psum 进入量化/激活级，随后以打包形式写入 Row buffer。
7. 一整行卷积结果准备好后，行级 PPU 读取 Row buffer，执行 Add、Affine、Concat、残差、Block5 合并和地址打包写回。

### 3.4 32x32 MAC 阵列与 K tile

当前阵列可以理解为 32 个输出通道 lane 与 32 个 K lane。一个 K tile 的抽象数据流如下：

```text
+------------------+   +------------------+   +------------------+
| K lane 0..31     |-->| Weight tile      |-->| Out lanes 0..31  |
+------------------+   +------------------+   +---------+--------+
                                                        |
                                                        v
                                      +-----------------------------+
                                      | 32 x 32 parallel INT8 MACs  |
                                      +--------------+--------------+
                                                     |
                                                     v
                                      +-----------------------------+
                                      | psum lane 0..31, K tile add |
                                      +-----------------------------+
```

满负载时，一个 K tile 最多包含 `32 x 32 = 1024` 个 INT8 MAC。这里有两种不同的并行性：

- **K tile 内并行**：32 个输入 lane 和 32 个输出 lane 同时工作；
- **K tile 间串行**：同一个输出位置的多个 K tile 必须依次累加，最后一个 tile 完成后才能得到最终 psum。

对于双位置模式，前 16 个输出 lane 处理第一个位置，后 16 个输出 lane 使用相同权重处理第二个位置。它主要减少窄通道卷积中的空槽，不改变阵列的理论峰值。

这不是传统的“数据在二维 PE 之间逐级移动”的 2D 脉动阵列。当前结构由 Window Generator 将输入窗口广播给多个输出 lane，partial sum 在输出 lane 内按 K tile 累加，再以 psum 数据包送入量化/激活级，更适合 ESPNet 的高分辨率、小通道和 1x1/3x3 混合卷积。

### 3.5 流水线与行边界

卷积行内部的流水关系如下。下面每一列是一个**抽象调度时间片**，用于表示数据在各级之间的先后关系，不宣称每一列严格等于一个物理时钟周期；实际耗时取决于 K tile 数、FIFO 状态和各级的 II。

```text
abstract time -->
             +----------+----------+----------+----------+----------+----------+----------+----------+
             |    S0    |    S1    |    S2    |    S3    |    S4    |    S5    |    S6    |    S7    |
             +----------+----------+----------+----------+----------+----------+----------+----------+
WindowGen    | x0:K0    | x0:K1    | x0:K2    | x1:K0    | x1:K1    | x1:K2    | x2:K0    | x2:K1    |
SA           |          | x0:K0    | x0:K1    | x0:K2    | x1:K0    | x1:K1    | x1:K2    | x2:K0    |
Requant/Act  |          |          |          | x0       |          |          | x1       |          |
Row buffer   |          |          |          | write x0 |          |          | write x1 |          |
             +----------+----------+----------+----------+----------+----------+----------+----------+
```

同一输出位置的 K0/K1/K2 必须先完成累加；不同输出位置的 x0/x1/x2 可以在 FIFO
允许时重叠。这里假设每个位置有 3 个 K tile，只用于展示关系。

读图时，`S0` 到 `S7` 只是等宽的抽象时间片，不是“每个 stage 固定占一个 clk”。例如 `x0:K0` 到 `x0:K2` 可能跨越多个真实时钟；当 `x0` 的 K tile 仍在 SA 中累加时，WindowGen 可以继续准备后续位置，只有 FIFO 满/空或最终 psum 尚未完成时才会停顿。

因此，当前并不是简单的“上一 cycle 在 WindowGen、下一 cycle 进 SA、再下一 cycle 进量化/激活”。更准确地说：

- WindowGen 以自己的供数节奏产生窗口 token；
- SA 在收到 token 后按 K tile 累加，同一个输出位置要连续处理多个 K tile；
- 量化/激活只能在该输出位置的最终 psum 到达后处理；
- FIFO 负责解耦各级，供数不足或下游阻塞时会产生 back-pressure。

所以当前已经存在的是**行内、不同输出位置之间的流水**，而不是固定一拍一级的锁步流水。

但卷积内部量化/激活与行级 PPU 并不是完全合并的单一流水。当前实际边界是：

```text
current row boundary (single shared Row buffer owner)

+------------------------------------------+
| row n: Conv + Requant/Act                |
| fill shared Row buffer                   |
+------------------------------------------+
                    |
                    v
+------------------------------------------+
| row n: Row PPU / writeback               |
| consume shared Row buffer                |
+------------------------------------------+
                    |
                    v
+------------------------------------------+
| row n+1: next Conv                       |
| starts after buffer owner release        |
+------------------------------------------+
```

这个边界的根本原因不是 SA 的数学依赖。不同输出行之间没有必须等待的 psum 累加关系，而是当前 Conv 和 PPU 共用同一个 Row buffer，存储所有权要求上一行先消费完成。当前还没有通过双 Row buffer 实现稳定的行间重叠。

从架构角度看，后续可以按复杂度分成两条路径：

- **简单路径**：`SA -> 量化/激活 -> Add/Affine -> 打包/写回`，直接流式连接，减少 Row buffer 往返；
- **复杂路径**：Block5、多分支 Concat 和需要残差对齐的操作保留 Row buffer，保证数据一致性。

再进一步，可以使用两个受控 Row buffer，使 `Conv(row n+1)` 与 `PPU(row n)` 重叠，但仍保持单一 Window Generator、单一 SA 和单一 PPU owner，避免复制核心和增加布线压力。

### 3.6 PPU、池化和最终输出

卷积后处理不是一个单独的通用 CPU 式模块，而是与行数据流相连的硬件路径：

- 普通行处理完成 Add、Affine、Concat、残差和紧凑写回；
- Block5 路径读取多路分支缓存，在行粒度完成合并、激活和最终写回；
- 独立向量阶段处理不紧跟卷积行的固定操作；
- 平均池化读取片上张量并完成通道累加；
- 最后一层输出经过定点上采样和类别比较，直接生成 `512x1024` 的 mask，避免保存完整的全分辨率多类别 logits。

### 3.7 当前架构的优点与下一步方向

当前设计已经实现了以下平衡：

- 用 PARAM 描述替代固定网络控制，支持二分类和 20 类模型；
- 用片上缓存和行复用降低高分辨率输入的存储开销；
- 用单一 32x32 MAC 阵列支持不同通道规模，避免复制多套计算核心；
- 用行级后处理减少中间张量写回；
- 用对称 INT8 量化省去零点补偿，简化 MAC 和量化路径。

当前性能瓶颈仍是卷积数据通路供数和 Conv/PPU 的串行边界。下一步应优先评估“单一卷积核心 + 两个小型 row buffer”的受控行间重叠，目标隐藏部分 Block5 和普通 PPU 时间；同时保持单一 WinGen、单一 SA 和单一后处理 owner。由于当前 BRAM 利用率已较高，任何双缓冲方案必须先通过资源、综合时间、100 MHz 布线和 fullres 精度回归门槛。
