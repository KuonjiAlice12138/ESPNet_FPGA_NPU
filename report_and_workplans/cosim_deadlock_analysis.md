# Analysis of C/RTL Co-simulation Deadlock Risk in Vitis HLS

## 1. Issue Overview
During the C/RTL co-simulation of the `espnet_encoder_int8_core`, a systemic hang (deadlock) occurs when execution enters the first convolutional layer using the stream-based dataflow architecture. 

## 2. Root Cause Analysis
The root cause is a **Producer-Consumer rate mismatch** on the `act_stream` (activation data stream) between the `window_generator` (Producer) and the `systolic_array_core` (Consumer). This issue manifests whenever a convolutional layer has more than 32 output channels (i.e., `TM = 32`, resulting in `oc_tiles > 1`).

### The Producer (`src/win_gen.cpp` -> `window_generator`)
The `window_generator` function iterates over the input spatial dimensions (`oh`, `ow`) and kernel tiles (`kt`). It generates the input activation window stream **exactly once** for the entire layer.

### The Consumer (`src/sa_core.cpp` -> `systolic_array_core`)
The `systolic_array_core` function contains an outermost loop iterating over the output channel tiles (`oc_tile_i`):
```cpp
for (int oc_tile_i = 0; oc_tile_i < MAX_C_TILE_COUNT; ++oc_tile_i) {
    if (oc_tile_i >= oc_tiles_i) break;
    // ... load weights ...
    for (int oh_i = 0; oh_i < MAX_FM_H; ++oh_i) {
        for (int ow_i = 0; ow_i < MAX_FM_W; ++ow_i) {
            for (int kt_i = 0; kt_i < MAX_SA_K_TILES; ++kt_i) {
                const act_vec_t act_word = act_stream.read(); // Blocked here!
                // ... MAC operations ...
```
Because the outermost loop iterates `oc_tiles_i` times, the consumer expects to read the entire activation feature map stream `oc_tiles_i` times. 

### Mechanism of Deadlock
1. During the first output channel tile (`oc_tile_i == 0`), the consumer successfully reads the activation data generated by the producer.
2. By the time the first tile finishes, the `window_generator` has completed its execution and exited.
3. The consumer advances to the second output channel tile (`oc_tile_i == 1`) and calls `act_stream.read()`.
4. Because the stream is implemented as a finite FIFO in RTL, and the producer has stopped sending data, the consumer hangs indefinitely, blocking the entire AXI interconnect and causing a co-simulation timeout/deadlock.

## 3. Log Evidence and Caveat
The C-simulation log (`cosim_logs/reuse_syn_top_golden_cosim_escalated_20260506_092104.out.log`) included:
> `INFO [HLS SIM]: The maximum depth reached by any hls::stream() instance in the design is 2097152`

This warning means C simulation allowed at least one stream to grow very deep because the dataflow processes are not modeled with final RTL FIFO depth. It is a useful risk signal, but it is not by itself proof of deadlock. In the current U04 case, the same warning can be produced by `psum_stream` accumulating a full-resolution output tile during C simulation even when `CONV.out_c <= TM` and activation producer/consumer counts match. The real structural deadlock risk remains the `act_stream` mismatch when `oc_tiles > 1`.

## 4. Adopted Architectural Fix

To safely re-enable `#pragma HLS DATAFLOW` execution, the design now uses the stream convolution path again but keeps the exporter/HLS contract that each `UOP_CONV` emits at most one output-channel tile:

```cpp
cfg.out_c <= TM
```

The current exporter already follows this rule by splitting wide tensors through multiple conv/store chunks. Under this contract, `window_generator` produces exactly `out_h * out_w * k_tiles` activation words and `systolic_array_core` consumes exactly the same count because `oc_tiles == 1`. If a future artifact violates this contract, `execute_conv_uop` returns `ERR_UNSUPPORTED_OPCODE` instead of entering a stream deadlock.

This is preferable to producer-side activation broadcasting for the current board because it does not multiply feature-map reads by `oc_tiles` and does not add large activation caches. It also matches the current parameter format, where one convolution qparam block contains 32 lanes.

### Alternatives Not Used Now

Producer-side broadcasting remains a possible future fallback if the design must support a single `UOP_CONV` with `out_c > TM`, but it would increase activation memory traffic and would also require multi-tile qparam/writeback handling. Consumer-side full-layer activation caching is not practical under the current BRAM/URAM limits.

## 5. Current Implementation State

`src/int8_core.cpp` now calls `execute_conv_stream_datapath` by default. The previous direct convolution fallback is retained behind `ESP_INT8_USE_DIRECT_CONV` for emergency comparison only.

The stream writeback path no longer performs unrolled reads from the same `hls::stream`; `out_stream` is drained with `PIPELINE II=1`, matching the PPU producer rate. `win_gen` also keeps the complex generic window-load loops conservative, while adding a pipelined 1x1 fast path and pipelined activation-word emission for the single-k-tile case. This restores the performance-critical stream path without adding full-layer activation caches or multiplying feature-map traffic.
